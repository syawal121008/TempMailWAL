# MASTER IMPLEMENTATION PROMPT — SYAWAL TEMPMAIL
 
## 1. PERAN DAN MISI
 
Bertindak sebagai Senior Full-Stack Engineer, Cloudflare Workers Engineer, React.js Developer, Security Engineer, dan UI/UX Designer.
 
Tugasmu adalah membangun fondasi aplikasi layanan disposable email atau Temp Mail bernama **Syawal TempMail** yang benar-benar berfungsi, aman, responsif, dan siap dikembangkan menjadi layanan publik.
 
Jangan hanya membuat mockup, prototype statis, atau demo dengan pesan email palsu. Implementasikan frontend, backend, database, pemrosesan email masuk, API, validasi, pengamanan, pengujian, dan dokumentasi deployment.
 
Prioritaskan implementasi bertahap, kode yang bersih, pemisahan tanggung jawab, keamanan, dan kompatibilitas dengan layanan hosting yang ditentukan.
 
Jika kamu memiliki akses ke repository atau terminal, periksa struktur dan kondisi proyek terlebih dahulu. Pertahankan konfigurasi yang masih valid dan jangan menghapus pekerjaan yang sudah ada tanpa alasan teknis yang jelas.
 
Jika belum ada proyek, buat struktur proyek lengkap dari awal.
 
Jangan mengklaim sesuatu sudah berhasil di-deploy, menerima email, atau lolos pengujian sebelum benar-benar diverifikasi.

## 2. KONDISI INFRASTRUKTUR SAAT INI
 
Domain proyek:
 
- Domain Temp Mail: `syawaltzy.my.id`
- Domain utama pemilik yang harus tetap terpisah: `syawaltzy.biz.id`
- Frontend hosting: Vercel
- DNS dan pengelolaan domain: Cloudflare
- Cloudflare Email Routing: sudah diaktifkan melalui dashboard
- Nameserver: sudah diarahkan ke Cloudflare
- Kondisi DNS saat ini: record DNS masih perlu diperiksa dan dikonfigurasi sesuai kebutuhan.
- Repository GitHub: belum ditentukan, periksa apakah sudah tersedia.
- API dan database: belum diasumsikan sudah dibuat.

 
PENTING: `syawaltzy.my.id` adalah domain untuk Temp Mail. Jangan mengubah, menghapus, atau mengganggu konfigurasi `syawaltzy.biz.id`.
 
Jangan menganggap DNS dan Email Routing sudah berfungsi hanya karena fiturnya telah diaktifkan di dashboard.
 
Periksa status konfigurasi dan tuliskan langkah yang masih diperlukan.

## 3. ARSITEKTUR TEKNOLOGI
 
Gunakan pembagian berikut:
 
### A. Frontend
 
- React.js
- Vite
- TypeScript
- Tailwind CSS
- Lucide React untuk ikon
- Fetch API atau client HTTP ringan
- Vercel untuk hosting frontend

 
Frontend bertanggung jawab atas tampilan, pembuatan dan pengelolaan inbox pengguna, countdown, tampilan pesan, serta komunikasi dengan API.
 
Jangan menyimpan email secara permanen hanya di React state atau localStorage.
 
### B. Backend API dan penerima email
 
Gunakan Cloudflare Workers dengan TypeScript.
 
Buat Worker yang memiliki dua tanggung jawab:
 
1. HTTP API untuk membuat inbox, mengambil pesan, menghapus inbox, dan mengelola sesi pengguna.
2. Email handler yang memproses email masuk menggunakan mekanisme Email Workers Cloudflare.

 
Gunakan worker bindings yang tepat dan pisahkan modul API HTTP dengan pemrosesan email agar pemeliharaan kode mudah.
 
### C. Database dan penyimpanan
 
Gunakan Cloudflare D1 untuk data terstruktur, misalnya:
 
- Inbox dan alamat email.
- Hash token akses.
- Waktu pembuatan dan kedaluwarsa.
- Metadata email.
- Status pesan.
- Identitas inbox pemilik pesan.

 
Jika diperlukan untuk email mentah atau lampiran, evaluasi Cloudflare R2 sebagai penyimpanan tambahan.
 
Jangan menyimpan lampiran tanpa batas. Batasi ukuran pesan, tipe lampiran, total penggunaan storage, dan retensi data.
 
### D. Infrastruktur
 
- Frontend: Vercel.
- DNS dan domain: Cloudflare.
- Backend: Cloudflare Workers.
- Database: Cloudflare D1.
- Penyimpanan pesan atau file opsional: Cloudflare R2.

 
Frontend, HTTP API, dan Email Worker harus berkomunikasi menggunakan kontrak API yang terdokumentasi.
 
Jangan berasumsi bahwa Vercel secara otomatis dapat menerima email masuk hanya dengan menambahkan domain.

## 5. ATURAN PEMBUATAN EMAIL SEMENTARA
 
Pengguna dapat membuat alamat email acak pada domain:
 
`@syawaltzy.my.id`
 
Contoh:
 
- `k8x2p9m4@syawaltzy.my.id`
- `m4q7z2n8@syawaltzy.my.id`
- `x9p3k6r2@syawaltzy.my.id`

 
Gunakan generator acak yang aman secara kriptografis, seperti Web Crypto API.
 
Persyaratan:
 
1. Pastikan alamat yang dihasilkan unik.
2. Validasi alamat di sisi server.
3. Simpan status aktif dan waktu kedaluwarsa di database.
4. Jangan menerima email untuk inbox yang sudah tidak ada atau kedaluwarsa.
5. Jangan menganggap alamat yang dibuat oleh frontend otomatis valid.
6. Terapkan perlindungan terhadap pembuatan inbox secara massal.
7. Tetapkan batas inbox aktif dan batas penggunaan berdasarkan konfigurasi.
8. Jangan menjanjikan jumlah email atau kapasitas yang belum didukung infrastrukturnya.

 
Masa aktif awal yang disarankan adalah 10 menit, tetapi nilainya harus dapat diatur melalui konfigurasi server.
 
Jika pengguna memilih masa aktif lain, server tetap harus memvalidasi batas yang diperbolehkan.
 
Penghapusan kedaluwarsa harus ditangani oleh backend atau scheduled cleanup, bukan hanya mengandalkan countdown frontend.

## 6. PENERIMAAN EMAIL SESUNGGUHNYA
 
Implementasikan penerimaan email masuk melalui Cloudflare Email Routing dan Email Worker.
 
Jangan mengimplementasikan pengiriman email keluar atau SMTP server publik.
 
Alur yang diharapkan:
 
1. Pengguna meminta pembuatan inbox melalui HTTP API.
2. API membuat local-part acak dan menyimpan record inbox di D1.
3. API memberikan alamat email dan token akses rahasia kepada browser.
4. Pengirim eksternal mengirim email ke alamat yang diberikan.
5. Konfigurasi Email Routing meneruskan email yang sesuai ke Email Worker.
6. Worker membaca penerima email dari envelope yang sebenarnya, bukan mempercayai header teks yang dapat dipalsukan.
7. Worker memeriksa apakah alamat penerima mempunyai inbox yang masih aktif.
8. Worker memproses MIME email menggunakan parser yang terpelihara dan sesuai untuk lingkungan Workers, contohnya PostalMime.
9. Worker menyimpan metadata dan konten pesan dalam database atau storage yang sesuai.
10. Inbox pengguna mengambil pesan melalui HTTP API yang terautentikasi.
11. Email dan metadata dihapus mengikuti kebijakan retensi.

 
Terapkan validasi ukuran pesan sebelum memproses atau menyimpan email. Jika batas ukuran dilampaui, tolak atau buang pesan dengan penanganan yang aman.
 
Jangan menerima lampiran berukuran tak terbatas.
 
Pastikan pemrosesan email tetap aman terhadap pesan MIME yang malformed, header tidak valid, konten terlalu besar, dan percobaan penyalahgunaan.
 
### Routing dan DNS
 
Periksa dokumentasi terbaru Cloudflare mengenai konfigurasi Email Routing dan Email Workers.
 
Periksa apakah domain sudah memiliki record MX dan TXT yang dibutuhkan.
 
Jika belum tersedia, jelaskan langkah untuk memperbaikinya melalui dashboard Cloudflare.
 
Jangan menganggap aktivasi Email Routing berarti email otomatis masuk ke Worker.
 
Jelaskan cara mengatur aturan routing agar alamat email sementara dapat diproses oleh Worker yang benar.
 
Jika implementasi menggunakan catch-all, pastikan Worker memeriksa penerima dan membuang email untuk inbox yang tidak dikenal atau kedaluwarsa.
 
Jangan mengarang tujuan MX, TXT, atau aturan routing.

## 7. DESAIN API
 
Implementasikan API versi pertama dengan struktur rute yang konsisten.
 
Contoh kontrak yang diharapkan:
 
- `POST /api/v1/inboxes` — membuat inbox.
- `GET /api/v1/inboxes/me` — melihat inbox milik sesi saat ini.
- `GET /api/v1/inboxes/me/messages` — mengambil daftar pesan.
- `GET /api/v1/inboxes/me/messages/:messageId` — membaca detail pesan.
- `DELETE /api/v1/inboxes/me/messages/:messageId` — menghapus pesan jika didukung.
- `DELETE /api/v1/inboxes/me` — menghapus inbox dan mengakhiri sesi.
- `GET /api/v1/health` — memeriksa kesehatan API tanpa mengungkap informasi sensitif.

 
Ini adalah contoh desain kontrak; implementasikan dan dokumentasikan kontrak final secara konsisten.
 
API harus menyediakan:
 
- Validasi input.
- Validasi autentikasi.
- Respons HTTP yang benar.
- Format JSON yang konsisten.
- Penanganan kesalahan.
- Batas ukuran request.
- CORS terbatas untuk origin yang diizinkan.
- Rate limiting.
- Pagination atau batas jumlah pesan per halaman.
- Pembatasan akses berdasarkan kepemilikan inbox.

 
Jangan membuat endpoint publik yang memungkinkan seseorang membaca inbox hanya dengan mengetahui alamat emailnya.

## 8. KEAMANAN WAJIB
 
Keamanan adalah persyaratan implementasi, bukan fitur tambahan.
 
### Autentikasi inbox
 
Gunakan token akses acak yang tidak mudah ditebak.
 
Token harus:
 
- Dibuat menggunakan generator kriptografis.
- Diberikan kepada pemilik inbox ketika inbox dibuat.
- Disimpan dalam bentuk hash di server apabila memungkinkan.
- Diperiksa pada setiap permintaan yang mengakses inbox.
- Tidak dimasukkan ke URL, query string, atau log.
- Tidak dapat digunakan untuk mengakses inbox pengguna lain.

 
Frontend boleh menyimpan sesi inbox pada penyimpanan browser yang sesuai, tetapi jangan menyimpan konten email secara permanen di localStorage.
 
Jangan mengklaim localStorage sepenuhnya aman terhadap XSS. Terapkan pencegahan XSS terlebih dahulu dan dokumentasikan risiko sesi browser.
 
### Perlindungan API
 
Terapkan:
 
- Rate limit pembuatan inbox.
- Rate limit pengambilan pesan.
- Pembatasan asal CORS.
- Validasi `Origin` sesuai kebutuhan dan jangan menjadikannya satu-satunya autentikasi.
- Validasi setiap parameter.
- Prepared statements untuk D1.
- Pembatasan request body.
- Penanganan error tanpa kebocoran stack trace.
- Pengamanan terhadap IDOR.
- Kebijakan retensi dan penghapusan pesan.
- Perlindungan terhadap abuse dan spam.

 
Gunakan Cloudflare Turnstile sebagai opsi yang dapat diaktifkan apabila memang dibutuhkan, dengan validasi token di sisi server.
 
Jangan menyimpan secret atau API key di kode frontend, repository publik, atau file konfigurasi yang di-commit.
 
Gunakan konfigurasi secret dan environment binding sesuai platform.
 
### Kebijakan email
 
Layanan ini hanya menerima dan menampilkan email masuk.
 
Jangan menyediakan relay SMTP publik, spoofing pengirim, ataupun fitur pengiriman massal.
 
Tampilkan peringatan bahwa inbox bersifat sementara dan tidak cocok untuk akun penting, pemulihan akun utama, atau menyimpan data sensitif.
 
Implementasikan penanganan email berbahaya dengan aman.
